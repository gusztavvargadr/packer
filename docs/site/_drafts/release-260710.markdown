## Lifecycle and evidence rules

- **Active** boxes participate in regular publication. **Deprecated** boxes remain hosted and documented but are no longer published regularly. **Removed** boxes must be absent from the registry, documentation and indexes, and all gist history.
- A deprecated box becomes eligible for a case-by-case removal decision one year after its newest registry version was published. Eligibility is not approval.
- Active-box cleanup retains `2601.0.0` and all `2607.*` versions. Other exact versions are candidates for separately approved routine registry cleanup; no R2 object is a cleanup candidate in this pilot.
- Component evidence is **missing** until an exact-version Azure transcript or completed HITL record establishes the installed versions. Alias records reuse the named canonical box evidence and must not duplicate component claims.

## Pilot observations for later automation design

- The public v2 user response is sufficient for public boxes, exact versions, providers, guest architectures, cumulative downloads, and descriptions, but expanded metadata or fetch redirects are required to prove alias targets.
- A catalog can change between discovery and execution: one exact version appeared 52 minutes after #582 was opened. Future automation needs a checksummed freeze and an explicit reconciliation gate.
- The 2601 gist is a catalog-level cumulative snapshot, not a version-download source. A newly added box legitimately has no prior row.
- The current baseline has 55 boxes: 41 active and 14 deprecated. The combined 2607 family has 58 exact version records across 40 boxes, with 217 records pairing a provider with a guest architecture, including 40 alias artifacts.
- All 58 exact 2607 version descriptions were blank at the freeze, and `windows-11-25h2-professional` was the only box with a blank box description.
