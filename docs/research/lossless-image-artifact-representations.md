# Lossless image artifact transfer representations

## Question

What does this repository actually transfer for Hyper-V, QEMU, VirtualBox, VMware, and their Vagrant boxes, and which temporary representations can expose reusable content while restoring the tested artifact byte-for-byte?

## Executive answer

The most promising shared representation is a versioned, content-addressed chunk bundle: split every artifact file with a deterministic content-defined chunker, store each distinct chunk once under its SHA-256 digest, and store an ordered manifest that reconstructs every original path and byte. It is intrinsically reversible, handles repeated zero/data regions, and can resynchronize after inserted or relocated bytes. Whether Azure Pipeline Artifact realizes the expected upload saving is a benchmark question, not a format fact.

Vagrant boxes need one extra layer. The Packer Vagrant post-processor used here produces a gzip-compressed tar at level 6, so chunking the `.box` bytes sees the compressed stream rather than the stable tar and disk payloads. A candidate should decompress only the gzip layer, content-chunk the exact raw tar stream, reassemble that stream, and recompress it with a helper pinned to the same pgzip implementation and parameters. This candidate is acceptable only if the reconstructed `.box` matches the pre-transfer SHA-256 on repeated cross-host trials. If it does not, preserving the current box bytes and exposing their uncompressed contents are competing requirements; do not silently substitute a logically equivalent archive.

Provider-native conversion and compaction remain useful before the artifact is tested and hashed, but `qemu-img convert`, `Optimize-VHD`, `VBoxManage` cloning/compaction, and `vmware-vdiskmanager` rewrite container bytes. They are not temporary transfer transforms unless an exact correction representation is also carried.

## Known facts

### Repository artifact boundary

The native build writes provider output below `image/` plus `manifest.json` and `checksum.sha256`; the Vagrant build writes `vagrant/vagrant.box` plus its manifest and checksum after consuming the native image. Azure publishes each whole build directory, and a separate Vagrant publish job downloads the Vagrant directory before publishing the box ([pipeline job](https://github.com/gusztavvargadr/packer/blob/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/.azure-pipelines/jobs.yml), [Windows native build](https://github.com/gusztavvargadr/packer/blob/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/src/windows/build.native.pkr.hcl), [Windows Vagrant build](https://github.com/gusztavvargadr/packer/blob/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/src/windows/build.vagrant.pkr.hcl)). The Packer checksum post-processor is already the authoritative SHA-256 producer, and publishing passes that value to the Vagrant registry.

The repository requests current compatible provider plugins rather than pinning exact plugin binaries: Hyper-V, QEMU, and Vagrant use `~> 1.1`, VirtualBox uses `~> 1.1.4`, and VMware uses `~> 1.2` ([provider templates](https://github.com/gusztavvargadr/packer/tree/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/src/windows)). Any byte-reproduction helper that depends on a plugin's compressor must therefore record and pin the resolved implementation, not just copy these constraints.

### Hyper-V

The native artifact is a Hyper-V export with `Virtual Hard Disks`, `Virtual Machines`, and, only when nonempty, `Snapshots` directly below `image/`; the repository derives later builds by locating a `.vmcx` below that tree ([repository source](https://github.com/gusztavvargadr/packer/blob/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/src/windows/source.hyperv.pkr.hcl), [Packer Hyper-V collation source](https://github.com/hashicorp/packer-plugin-hyperv/blob/f9151aad757f2c9fc407b1a149bf22d05167b2f7/builder/hyperv/common/step_collate_artifacts.go)). The main payload is a dynamic VHDX unless fixed VHD was explicitly requested; this repository does not request fixed disks.

VHDX is internally block allocated. Its file contains headers, a log, metadata, a block allocation table, payload blocks, and optional sector-bitmap blocks; structures are 1 MiB aligned, and each BAT entry maps a virtual block state and physical file offset ([VHDX layout](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-vhdx/89270f3c-94c9-4363-a678-92b1ca7990a0), [BAT](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-vhdx/af7334e6-ad2c-4378-9b81-afc1334a6ee7), [payload states](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-vhdx/01da203b-b3d7-487d-928b-22a460bbe177)). A dynamic VHDX can represent zero or absent payload blocks without allocating their payload bytes.

The Packer Hyper-V plugin already runs `Optimize-VHD -Mode Full` on every VHD/VHDX before exporting unless `skip_compaction` is true ([plugin compaction step](https://github.com/hashicorp/packer-plugin-hyperv/blob/f9151aad757f2c9fc407b1a149bf22d05167b2f7/builder/hyperv/common/step_compact_disk.go), [PowerShell implementation](https://github.com/hashicorp/packer-plugin-hyperv/blob/f9151aad757f2c9fc407b1a149bf22d05167b2f7/builder/hyperv/common/powershell/hyperv/hyperv.go)). Microsoft documents that `Optimize-VHD` reclaims unused blocks and rearranges blocks to pack them more efficiently, but may produce no reduction when no further optimization is possible ([Optimize-VHD](https://learn.microsoft.com/en-us/powershell/module/hyper-v/optimize-vhd)). The repository therefore already receives format-native compaction before hashing.

### QEMU

The repository explicitly chooses QCOW2, enables `detect-zeroes=unmap`, and drops the copied EFI variables file, leaving the QCOW2 disk as the main native payload ([repository source](https://github.com/gusztavvargadr/packer/blob/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/src/windows/source.qemu.pkr.hcl)). QCOW2 allocates metadata and guest data in clusters, maps guest clusters through L1/L2 tables, and represents unallocated clusters without a host offset; compressed clusters are possible but are a distinct descriptor state ([QCOW2 specification](https://www.qemu.org/docs/master/interop/qcow2.html)).

Packer's QEMU builder compacts QCOW2 by running `qemu-img convert -O qcow2` unless `skip_compaction` is true. It adds `-c` only when `disk_compression` is true, which this repository does not set ([plugin configuration](https://github.com/hashicorp/packer-plugin-qemu/blob/cdf6040f44b13053a197806fab47ffd33af0b0a2/builder/qemu/config.go), [conversion step](https://github.com/hashicorp/packer-plugin-qemu/blob/cdf6040f44b13053a197806fab47ffd33af0b0a2/builder/qemu/step_convert_disk.go)). QEMU documents that conversion suppresses empty sectors for growable output, while `-c` creates read-only compressed clusters for QCOW/QCOW2; `-S` controls the zero run that becomes sparse ([qemu-img](https://www.qemu.org/docs/master/tools/qemu-img.html)). The native QCOW2 is therefore compacted but not format-compressed under the present configuration.

### VirtualBox

Although VirtualBox uses VDI while constructing a VM, this repository's native artifact is not normally a VDI. The repository leaves the Packer VirtualBox export format at its default `ovf`; the plugin calls `VBoxManage export` and writes an `.ovf` plus its disk files ([repository source](https://github.com/gusztavvargadr/packer/blob/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/src/windows/source.virtualbox.pkr.hcl), [plugin export configuration](https://github.com/hashicorp/packer-plugin-virtualbox/blob/b6e81112919ed50bf8a0a35438a0709098ad0d27/builder/virtualbox/common/export_config.go), [plugin export step](https://github.com/hashicorp/packer-plugin-virtualbox/blob/b6e81112919ed50bf8a0a35438a0709098ad0d27/builder/virtualbox/common/step_export.go)). Oracle documents that OVF appliances contain VMDK disks and that those appliance VMDKs are compressed and cannot be used directly by a VM until import ([VirtualBox OVF documentation](https://docs.oracle.com/en/virtualization/virtualbox/7.1/user/Introduction.html)). This explains why VirtualBox native artifacts may behave more like already-compressed content; the hypothesis should be tested against actual file listings, but "compressed VDI" is not the expected layout here.

VirtualBox's `modifymedium --compact` removes all-zero blocks from dynamically allocated images without changing logical capacity, but Oracle documents it as VDI-only; non-VDI images require zeroing free blocks and cloning to another dynamically allocated image ([VBoxManage](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/vboxmanage.html)). That operation applies to the construction VDI, not directly to the already-exported compressed appliance VMDK.

### VMware

The repository sets `disk_type_id = 0`, which the Packer VMware plugin defines as a growable monolithic-sparse VMDK in one file; the native output format defaults to `vmx`, so its `image/` directory contains the VMDK plus VMX and supporting VM files rather than an OVA ([repository source](https://github.com/gusztavvargadr/packer/blob/a2d66dc4830ee45fd9647b7e122ecdd526c89b1a/src/windows/source.vmware.pkr.hcl), [plugin disk types](https://github.com/hashicorp/packer-plugin-vmware/blob/4e48f4baee0bb91da89b391afc7a79b0d7a5552d/builder/vmware/common/disk_config.go), [plugin output default](https://github.com/hashicorp/packer-plugin-vmware/blob/4e48f4baee0bb91da89b391afc7a79b0d7a5552d/builder/vmware/iso/config.go)). Broadcom likewise describes monolithic sparse as one VMDK that grows as needed ([Virtual Disk API](https://developer.broadcom.com/xapis/virtual-disk-api/latest/vddkDataStruct.5.3.html)).

The Packer VMware plugin runs the host `vmware-vdiskmanager` defragment and shrink operations before output unless `skip_compaction` is true ([plugin compaction step](https://github.com/hashicorp/packer-plugin-vmware/blob/4e48f4baee0bb91da89b391afc7a79b0d7a5552d/builder/vmware/common/step_compact_disk.go), [Fusion implementation](https://github.com/hashicorp/packer-plugin-vmware/blob/4e48f4baee0bb91da89b391afc7a79b0d7a5552d/builder/vmware/common/driver_fusion.go)). The repository does not disable that step. VMware's Vagrant documentation explicitly says ordinary VMware disks are not compressed and recommends gzip-compressing the final box ([VMware box format](https://developer.hashicorp.com/vagrant/docs/providers/vmware/boxes)).

### Vagrant boxes

Vagrant accepts a box as `tar`, `tar.gz`, or `zip`, with provider VM artifacts, required `metadata.json`, and optional `Vagrantfile`/`info.json` ([box file format](https://developer.hashicorp.com/vagrant/docs/boxes/format)). This repository uses the Packer Vagrant post-processor, whose default is compression level 6 ([Packer Vagrant documentation](https://developer.hashicorp.com/packer/integrations/hashicorp/vagrant/latest/components/post-processor/vagrant)). Its implementation creates a GNU-format tar and wraps it in pgzip unless compression level 0 is selected; the current source pins pgzip 1.2.6 and configures 500,000-byte blocks with `runtime.GOMAXPROCS` concurrent workers ([archive implementation](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/post-processor/vagrant/util.go), [dependency](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/go.mod)). Compression is therefore an outer transform shared by every provider, not a ZIP file as initially suspected.

Provider contents below that gzip/tar layer differ. VirtualBox copies the OVF appliance's compressed VMDK and renames the descriptor to `box.ovf`; VMware copies the VMX/VMDK files; QEMU copies the QCOW2 disk to `box_0.img` and records it in metadata; Hyper-V preserves the exported nested directories ([VirtualBox packaging source](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/post-processor/vagrant/virtualbox.go), [VMware packaging source](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/post-processor/vagrant/vmware.go), [libvirt packaging source](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/post-processor/vagrant/libvirt.go), [Hyper-V packaging source](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/post-processor/vagrant/hyperv.go)). Thus removing only the outer gzip should expose reusable regions for Hyper-V, QEMU, and VMware; VirtualBox may retain poor reuse because its inner VMDK is already compressed.

The current Packer Vagrant Registry post-processor assumes a gzip reader followed by a tar reader when inspecting `metadata.json`, even though Vagrant core accepts other box encodings ([registry source](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/post-processor/hcp-vagrant-registry/post-processor.go)). Changing the permanent box to uncompressed tar or ZIP would therefore also require changing this publish path; it is not a drop-in transfer-only adjustment.

## Exact-byte candidate representations

### Candidate A: content-addressed chunks for every native artifact

Define `image-transfer/v1` as a small manifest plus a `blobs/sha256/<digest>` set. For each regular artifact file, record its relative path, byte length, full-file SHA-256, ordered chunk digest/length pairs, and required mode metadata; reject absolute paths, `..`, duplicate normalized paths, links, devices, and unknown entry types. Split large files with one fixed content-defined chunking policy and store each unique chunk once. Restic is a production example of this model: it uses Rabin-fingerprint content-defined chunking, stores an ordered hash list per file, and only saves changed blobs even when insertions or removals shift later bytes ([restic design](https://github.com/restic/restic/blob/master/doc/design.rst)).

Reconstruction creates a fresh destination, concatenates chunks in manifest order, checks every chunk digest and length while reading, checks every complete file, rejects missing or extra paths, and finally checks the repository's original `checksum.sha256` before exposing the directory to Packer or Vagrant. Renaming the staging directory into place only after validation prevents consumers from seeing partial data.

This representation preserves file bytes exactly and can collapse repeated chunks, including long zero regions, into one stored blob. If retaining sparse allocation on the receiving filesystem matters, the manifest can additionally record holes discovered through supported filesystem extent APIs and recreate them with seeks; sparse allocation is not part of a file's byte checksum and must not replace byte validation.

Costs are one full sequential read and hash pass, chunk-boundary calculation, a staging bundle, and one full reconstruction pass. The build hosts have enough CPU and disk for this, but measured transform time, peak staging bytes, number of blob files, upload bytes, and end-to-end restore time decide the result. Benchmark fixed-size chunks as a simpler control against content-defined chunks; virtual-disk rewrites can relocate blocks, so content-defined chunking is expected, but not yet proven, to resynchronize better.

### Candidate B: remove the Vagrant gzip layer during transfer

For a completed and hashed `vagrant.box`, stream-decompress gzip into the exact raw tar byte stream without extracting it, feed that tar stream through Candidate A, then reconstruct the identical tar and gzip it with a small helper pinned to the exact pgzip and compression settings resolved in the build. This avoids archive path traversal during the transfer transform because it never materializes archive members. It also preserves the original tar headers, entry order, padding, modes, and timestamps automatically.

The [pgzip 1.2.6 source](https://github.com/klauspost/pgzip/blob/v1.2.6/gzip.go) initializes a fixed empty gzip header and uses a configured block size, which makes exact recompression plausible, but exactness is a hypothesis until measured across the actual Windows, Linux, and macOS build/publish host combinations. The acceptance condition is simple: the reconstructed `.box` SHA-256 and byte length must equal the original on every trial. If it fails, capture the complete compressor/plugin dependency versions and first differing offset, then either pin a reproduction helper more tightly or reject the approach. Logical equivalence from `vagrant box add` is insufficient.

If chunking the intact tar still gives poor reuse, `tar-split` is a higher-complexity variant that records raw tar metadata and payload offsets so it can pristinely reassemble the original tar while exposing each member payload independently ([tar-split README](https://github.com/vbatts/tar-split)). Its documented caveats around sparse tar entries and duplicate paths must be treated as hard validation failures. Packer's box writer skips directory entries and archives ordinary files, so the expected boxes appear compatible, but actual boxes must be scanned before adopting it.

### Candidate C: exact binary delta against an available basis

When the job already downloads a base native artifact, a binary delta from that exact basis to the derived native artifact can be much smaller and still reconstruct the output byte-for-byte. Record the basis artifact SHA-256 in the manifest, refuse the delta if the basis is unavailable or mismatched, reconstruct into a new file, and verify the target SHA-256. This is secondary rather than the shared default because allocation-table churn and compressed streams can make a generic delta large, and cross-run basis retention is not a hard requirement.

### Representations that do not meet the byte identity rule by themselves

Converting VHDX, QCOW2, VDI/VMDK, or VMDK to sparse raw and back preserves guest-visible disk sectors when done correctly, but it does not reproduce the original container metadata, allocation order, UUIDs, logs, or compressed bitstream. `qemu-img compare` or a mounted filesystem test can establish logical equivalence, not artifact byte identity. These conversions are valid experiments only before testing/hashing establishes a new canonical artifact, or when paired with an exact correction/delta representation and final SHA-256 verification.

Ordinary archive extraction followed by `tar`/`gzip` recreation also does not promise byte identity. Tar entry order, raw header form, ownership fields, timestamps, padding, and gzip implementation parameters can all change. Preserve the raw tar stream or use a proven exact tar disassembler; never infer success from equal extracted files.

Splitting the existing `.box` into fixed pieces and concatenating them is reversible, but compression can cause a changed early region to alter a long suffix of compressed bytes. It is a useful control benchmark, not a credible explanation-free fix.

## Hyper-V `box.xml` correctness requirement

The affected Hyper-V export contains both `Virtual Machines/box.xml` and a `.vmcx`. Vagrant's current Hyper-V import code accepts `.xml` and `.vmcx`, iterates the directory, and stops at the first matching entry ([Vagrant import source](https://github.com/hashicorp/vagrant/blob/35f3160f4ad6edc3a9f3aa9570adfc1a4d73aaa5/plugins/providers/hyperv/action/import.rb)). Consequently, selection is not guaranteed to prefer `.vmcx`. The confirmed workaround in [issue 469](https://github.com/gusztavvargadr/packer/issues/469) is to remove `Virtual Machines/box.xml`, after which Vagrant imports the exported `.vmcx`; the upstream Packer issue documents that `box.xml` drives the older `New-VM` reconstruction path ([packer-plugin-vagrant issue 23](https://github.com/hashicorp/packer-plugin-vagrant/issues/23)).

Removal must occur before Vagrant testing and before the final SHA-256 is generated. The current Vagrant post-processor copies every Hyper-V artifact file into its temporary box tree, so it has no exclusion hook ([Hyper-V packaging source](https://github.com/hashicorp/packer-plugin-vagrant/blob/0467e38db5a95a723ef19bf11ca7386a405e6bcb/post-processor/vagrant/hyperv.go)). The clean implementation seam is the same shared packaging helper used for transfer preparation: after Packer creates the preliminary box, validate the gzip/tar, remove exactly the normalized regular-file path `Virtual Machines/box.xml` only for provider `hyperv`, rebuild the box, assert that at least one `.vmcx` remains under `Virtual Machines`, then compute `checksum.sha256` and run the existing Vagrant test. Alternatively, add an upstream-style exclusion option to the Packer Vagrant post-processor; either route requires moving the current checksum operation after removal.

Archive rewriting must reject absolute paths, traversal components, case-colliding or duplicate normalized names, symbolic/hard links for the target, non-regular target entries, and more than one target. Write to a new file on the same volume, validate the rebuilt archive and expected entries, compute its SHA-256, then atomically replace the preliminary box. This is an intentional canonical-artifact change, not a temporary transfer repackage, so the rebuilt box is the one that must be tested, hashed, transferred, and published.

## Benchmark hypotheses and decision gates

The following are hypotheses, not findings from baseline logs or Azure task internals:

- Candidate A should improve native cross-run reuse most for compacted but uncompressed VHDX, QCOW2, and monolithic-sparse VMDK, while its manifest overhead and file count remain manageable.
- Candidate B should substantially improve box reuse for Hyper-V, QEMU, and VMware by removing the outer gzip during transfer; exact pgzip reproduction and total transform time are the first gates.
- VirtualBox should remain the hardest case because `VBoxManage export` creates a compressed appliance VMDK before the outer box gzip. If Candidate B underperforms only there, benchmark a provider-specific pre-test canonical format or exact-delta correction rather than weakening the shared default for every provider.
- Re-running provider compactors after hashing will break the byte checksum and must fail the design. Adjusting compaction before hashing can reduce future artifacts but is a production-format experiment, not a transfer representation.
- Content-defined chunks should outperform fixed chunks when compactors relocate unchanged payload; fixed chunks may be faster and sufficient when offsets remain stable. Measure both before choosing.

For each candidate, record original logical bytes, staged representation bytes, distinct blob bytes/count, transform CPU and wall time, upload wall time and reported physical bytes, download wall time, reconstruction wall time, peak temporary disk, and full SHA-256 result. Run on one clean agent first. Only candidates that reduce upload bytes/time without worsening the complete transform-upload-download-restore path beyond the agreed threshold advance to two simultaneous home-lab agents.

## Recommended prototype order

1. Inventory one Windows and one Ubuntu artifact per available provider with path, logical size, allocated size where the host exposes it, detected disk subformat, and current SHA-256; confirm the layouts above.
2. Prototype Candidate A as a provider-neutral directory transform and compare fixed-size versus content-defined chunks on native artifacts from two adjacent builds.
3. Prove or disprove exact pgzip reconstruction of existing boxes before building Candidate B's full chunk bundle.
4. Apply the validated Hyper-V `box.xml` rewrite before test/hash and add the resize/boot regression from issue 469 to the Hyper-V acceptance check.
5. If VirtualBox remains an outlier, test a measured provider-specific representation; do not introduce one based solely on the format theory.

## Limitations

This research inspected repository configuration and primary specifications/source. It did not download the large build artifacts, scrape the linked Azure logs, or benchmark Azure's transfer implementation; those measurements and Azure mechanics are intentionally owned by separate tickets. Exact filenames can also vary by host/provider version, so the first inventory step is mandatory. The pgzip reconstruction claim remains explicitly unproven until byte-for-byte trials run with the resolved plugin binaries.
